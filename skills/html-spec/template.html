1. Summary

One or two sentences: what this change does. If it implements a roadmap row, name the roadmap and the row ID here.

2. Problem

What hurts today, and for whom. Written so the reader can judge whether the requirements below actually solve it.

3. Scope & Non-Goals

In scope

  • The capability this change delivers, stated as an outcome someone can demonstrate.

Non-goals

  • Explicitly out of scope. State these — do not rely on omission.

4. Conformance

Key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in RFC 2119.

Producer requirements (allowed input)

  • What a user, client, or upstream system is allowed to supply.

Consumer requirements (required behavior)

  • How this system must act in response — including on malformed input.

5. Requirements

IDLevelRequirement
FR-1 MUST A testable assertion. The system MUST do something specific enough that a test can pass or fail on it.

Note: non-normative rationale — why a rule exists, so it generalizes to cases this spec did not anticipate.

6. Acceptance Criteria

AC-1 (satisfies FR-1)

  • Given the starting state.
  • When the action happens.
  • Then a measurable, binary outcome.

7. Behavior

  1. First step.
  2. If a condition holds, do this and stop.
  3. Otherwise, continue.

Example: illustrative only — one valid case, not the only allowed one.

8. Design

The approach in two to four sentences. Everything implementation-specific belongs here, not in the requirements.

ASCII architecture sketch, if it helps.

Key decisions

  • Decision: the reason it was chosen over the alternative.

Security considerations

  • Permissions, data flows, new dependencies, input handling.

9. Evidence & Limits

  • Checked: the tests, contracts, fixtures, schemas, configuration, and runbooks actually inspected, and what each validates.
  • Unverified: behavior that is inferred, untested, or contradictory.

Warning: a passing suite demonstrates only the behavior it covers. Do not claim completeness the evidence does not support.
